# PR Studio 2.0 최종 프레임 OCR 수리 계획

- 작성일: 2026-10-26
- 대상 브랜치: `agent/pr-studio-2.0`
- 선행 커밋: `43ef4d9b40c166de13830804028f00f37711faa1`
- 재현 환경: Railway `staging`
- 재현 작업: `4877e082-6f99-4011-b600-b7c6ddec5bf2`

## 1. 고정 목표

PR Studio 2.0은 화려한 영상을 만드는 범용 편집기가 아니다. 목적과 대상에 맞는 콘텐츠를 먼저 판단하고, 자연스러운 음성과 간결한 자막, 목적에 맞는 화면을 결합한 뒤 실제 최종 MP4에서 그 내용이 전달되는지를 검증하는 도구다.

이번 수리는 이 목표를 바꾸지 않는다. 특히 다음 조건은 낮추지 않는다.

1. 실제 앱 화면에서 계획한 핵심 근거를 확인해야 한다.
2. 최종 MP4에서도 그 핵심 근거가 보이는지 검사해야 한다.
3. OCR 또는 검증 도구가 있다는 이유만으로 실패를 무조건 통과시키지 않는다.
4. 기술 조건과 콘텐츠 조건을 모두 통과해야만 영상을 완료한다.

## 2. 재현 결과

동일 MP4와 유튜브 트랙으로 스테이징 전체 흐름을 실행했다.

- 1차 기획은 실제 유튜브 제작 화면과 기존 영상 분석을 요청했다.
- Chromium 수집은 유튜브 화면에 예시를 입력하고 생성한 뒤 실제 결과 문구를 확인했다.
- 기존 MP4는 52.6초로 분석됐다.
- 2차 기획은 누적 근거를 읽고 제작을 승인했다.
- 최종 MP4는 1920×1080, 오디오 포함, 65.289초, 2,303,592바이트로 기술 검사를 통과했다.
- 같은 작업은 세 번 전체 재시도됐다. 1·2차에는 `youtube-input`, `youtube-generate`, `youtube-output`이 누락됐고, 3차에는 `youtube-generate`, `youtube-output`만 누락됐다. 동일 계약의 판정 결과가 실행마다 달랐다.
- 최종 콘텐츠 검사에서 `youtube-generate`, `youtube-output`의 `YouTube 게시 패키지`를 단일 중간 프레임 OCR이 찾지 못해 `contentReady: false`가 됐다.
- 세 번 모두 기술 조건은 통과했지만 MP4 크기는 2,253,807 → 2,342,051 → 2,303,592바이트로 달라졌다. 현재 재시도는 검토만 다시 하는 것이 아니라 캡처·TTS·렌더 전체를 반복한다.

품질 게이트가 실패를 숨기지 않은 것은 올바른 동작이다. 문제는 최종 장면 확인 방식이 실제 화면 계약보다 취약하다는 데 있다.

## 3. 근본원인

### 3.1 단일 프레임만 검사한다

검토기는 각 beat의 정확한 중간 시점 한 장만 추출한다. 동작 장면에서는 결과 패널이 나타나는 시점과 중간 시점이 어긋날 수 있다. 한 프레임의 선택 오차가 장면 전체의 실패로 처리된다.

### 3.2 전체 1920×1080 프레임을 그대로 OCR한다

검증 대상 문구는 결과 패널의 일부지만 Tesseract에는 내비게이션, 본문, 자막이 모두 포함된 전체 화면이 들어간다. 작은 한국어 제목은 배경 정보와 자막에 묻혀 인식률이 떨어진다.

### 3.3 캡처 때 확보한 위치 정보를 버린다

캡처 단계는 Playwright로 정확한 `observe` 요소를 찾지만, 로그에는 그 요소의 위치가 남지 않는다. 최종 검토가 이미 확인한 대상 영역을 재사용하지 못하고 전체 화면 OCR로 되돌아간다.

### 3.4 DOM 존재와 녹화 화면 안의 가시성을 혼동한다

현재 캡처는 결과 문구가 DOM에 생길 때까지 기다리고 `innerText`를 읽지만, 해당 요소를 녹화 뷰포트 안으로 스크롤하지 않는다. 유튜브 결과 패널은 긴 대본과 여러 결과 영역 뒤에 있어 `YouTube 게시 패키지`가 실제 1920×1080 화면 아래에 남을 수 있다. 이 경우 OCR이 틀린 것이 아니라 영상에 근거가 실제로 없으므로 반드시 캡처 단계에서 실패해야 한다.

### 3.5 OCR 실행 환경에 대한 회귀 검증이 없었다

기존 단계 6 검증은 로컬에 Tesseract가 없어 `ocrStatus: skipped` 상태에서 직접 프레임을 확인했다. Railway의 `kor+eng` OCR 경로가 실제로 처음 실행된 이번 스테이징 작업에서 단일 프레임·전체 화면 방식의 취약점이 드러났다.

### 3.6 재시도가 새 산출물을 만들어 판정 원인을 섞는다

현재 워커는 최종 콘텐츠 검토 실패도 일반 실행 오류와 똑같이 처리한다. 재시도 때 캡처부터 렌더까지 새로 수행하므로 같은 영상을 재검증하는 것이 아니라 조금씩 다른 MP4를 다시 만든다. 그 결과 OCR 판정의 비결정성과 제작 결과의 변동이 섞여 근본원인 추적과 감사가 어려워진다.

## 4. 수리 자체가 만들 수 있는 문제

### 품질 게이트 약화 위험

부분 문자열을 줄이거나 `YouTube` 한 단어만 보이면 통과시키면 다른 화면도 오인할 수 있다. 따라서 기대 문구 자체는 완전한 `observe` 계약으로 유지한다.

### 좋은 프레임만 골라 통과시키는 위험

여러 프레임 중 하나만 통과시키면 순간적으로 스친 화면도 승인될 수 있다. 샘플은 beat 후반의 제한된 복수 시점으로 고정하고, 캡처 당시 확인한 정확한 관찰 영역만 검사한다.

### 좌표 변환 오류 위험

`*-output` 정지 화면은 렌더러가 확대·크롭한다. 원본 요소 좌표를 그대로 쓰면 다른 영역을 OCR할 수 있다. 렌더러의 실제 변환과 같은 계산을 한 곳의 순수 함수로 고정하고 테스트한다.

### 검증 시간 증가

모든 beat 전체 화면을 여러 번 OCR하면 Railway 실행 시간이 크게 늘어난다. 앱 화면 beat마다 2~3개의 작은 관찰 영역만 OCR하고, 첫 성공 뒤 나머지 OCR을 중단한다.

### 원래 목표와의 충돌 여부

충돌하지 않는다. 화면 화려함을 추가하는 수리가 아니라, 계획한 핵심 콘텐츠가 최종 영상에 실제로 보이는지를 더 정확히 판정하는 수리다. 음성·자막·기술 검사는 그대로 유지한다.

## 5. 단계별 구현 계획

### 단계 A — 실제 가시성 계약과 안정 구간 확보

1. track별 결과 제목에 전용 `data-*` 관찰 표식을 두고 유일성을 검사한다. 페이지 전체의 느슨한 텍스트 locator는 사용하지 않는다.
2. 결과가 준비되면 정확한 관찰 요소를 결정론적으로 화면 중앙의 자막 비중첩 안전 영역으로 스크롤한다.
3. 요소 전체가 1920×1080 뷰포트와 정의된 안전 영역 안에 들어왔는지 검사한다. 원래 box가 화면 밖이면 좌표를 자르지 않고 캡처를 실패시킨다.
4. 결과 화면이 안정된 뒤 `stableFromMs`와 `stableToMs`를 기록하고 최소 관찰 유지 시간을 실제 녹화한다.
5. 동작 클립은 저장한 캡처 종료 시점에서 자르고 마지막 안정 프레임을 패딩해 다음 beat가 섞이지 않게 한다.

완료 기준:

- DOM 존재가 아니라 실제 녹화 뷰포트 안의 가시성이 보장된다.
- 관찰 요소가 안전 영역 밖이면 제작을 계속하지 않는다.
- 동작 클립의 검증 가능 안정 구간이 시간 정보로 남는다.

### 단계 B — 캡처 관찰 근거와 좌표 변환 보존

1. `observedText`를 얻은 동일한 전용 locator의 `boundingBox`를 캡처 로그에 저장한다.
2. 캡처 viewport 크기, 검증 대상 문구, 안정 시각을 함께 기록한다.
3. 최종 프레임 샘플 시점, 관찰 영역 확대 여백, 출력 화면 확대·크롭 좌표 변환을 순수 함수로 분리한다.
4. CSS 좌표 → 캡처 픽셀 → 확대 → 중앙 크롭 → 여백 확장 → 여백만 경계 제한 순서를 명시적으로 구현한다.
5. FFmpeg의 실제 시각 변환과 검증 좌표가 같은 변환 계약을 사용하게 한다.

완료 기준:

- 각 앱 beat가 `observationBox`, `captureViewport`, `observedText`, 안정 구간을 가진다.
- 기존의 DOM 실제 문구 확인은 그대로 유지된다.
- `youtube-output` 확대·크롭 후에도 원래 관찰 요소의 영역을 정확히 가리킨다.

### 단계 C — 최종 MP4의 대상 영역 OCR

1. 각 앱 beat의 기록된 안정 구간에 대응하는 제한된 시점에서 최종 MP4 프레임을 추출한다.
2. 캡처 로그의 관찰 영역을 렌더 변환에 맞춰 매핑하고 적절한 여백을 포함해 자른다.
3. 작은 영역을 확대해 `kor+eng` OCR을 실행한다.
4. 동작 장면은 시간순으로 인접한 두 샘플 이상에서 정규화된 전체 `observe` 문구가 일치해야 한다. 정지 장면은 안정된 한 장의 대상 영역에서 전체 문구가 일치해야 한다.
5. 제작 경로에서는 Tesseract, `kor+eng` 데이터 또는 OCR 명령이 없거나 실패하면 fail-closed한다. 로컬 우회는 명시적인 개발 전용 옵션으로만 허용한다.
6. `review.json`에 시점별 원본 프레임, crop, 좌표, OCR 텍스트, 일치 여부와 MP4 SHA-256을 남긴다.

완료 기준:

- 검증 대상 문구를 축약하지 않고 최종 MP4 안에서 확인한다.
- 순간적으로 한 번 나타난 문구만으로 동작 장면을 통과시키지 않는다.
- 실패 시 어떤 프레임과 영역을 검사했는지 감사 가능하다.

### 단계 D — 실패 비용과 오류 가시성

1. 최종 검토 실패 메시지에 `review.json`의 핵심 결과와 MP4 해시를 유지한다.
2. 콘텐츠 불일치는 동일 산출물의 최종 실패로 분류하고 전체 재렌더를 금지한다.
3. OCR 프로세스·언어 데이터 등 검토 인프라 오류는 동일 MP4의 검토 단계만 제한 횟수 재시도하며, 그래도 실패하면 새 MP4를 만들지 않고 종료한다.
4. 캡처·TTS·렌더 인프라 오류만 기존 작업 재시도 대상으로 둔다.
5. 콘텐츠 검토 실패 시 해당 시도의 MP4, `review.json`, crop 근거를 결과 저장소의 감사 경로에 보존한다.

완료 기준:

- 품질 실패의 이유가 UI와 로그에서 식별된다.
- 같은 콘텐츠 실패 때문에 서로 다른 MP4를 세 번 새로 만들지 않는다.

### 단계 E — 검증

1. 좌표·안정 구간 샘플링·연속 OCR 판정 단위 테스트.
2. 화면 밖 box, 잘못된 box, 잘못된 문구, 한 프레임만 일치하는 동작 장면이 통과하지 않는 음성 테스트.
3. FFmpeg 확대·크롭 fixture와 좌표 계산을 비교하는 픽셀 수준 테스트.
4. 실제 인코딩된 CJK 프레임의 crop→확대→OCR 통합 테스트를 Tesseract 사용 환경에서 실행.
5. `npm test`, `npm run lint`, `npm run build`.
6. 로컬에서 Tesseract가 있으면 실제 유튜브 영상 smoke, 없으면 Railway에서 `kor+eng` 존재와 실제 OCR을 반드시 검증.
7. 동일한 불변 MP4를 세 번 검토해 판정과 OCR 근거가 같은지 확인.
8. 스테이징 재배포 후 동일 MP4·동일 브리프로 전체 작업 재실행.
9. `ffprobe`, 최종 프레임, OCR 기록, MP4 해시, 전체 영상 시청으로 화면·음성·자막 일치를 확인.

## 6. 감사 원칙

- 이 계획은 구현 전에 독립 감사를 받는다.
- 감사는 고정 목표를 바꾸지 않는다.
- 품질 게이트를 강화하거나 오류 가능성을 줄이는 좋은 의견은 수용한다.
- 구현 후에는 코드, 테스트, Railway 실제 작업, 최종 MP4를 다시 독립 감사한다.
