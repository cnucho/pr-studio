# PR Studio 2.0 영상 종류 수집 불일치 수리 계획

- 작성일: 2026-10-26
- 대상 브랜치: `agent/pr-studio-2.0`
- 기준 커밋: `b398653`
- 결함 증거 작업: `b677ce3d-42a1-4e31-bce8-bd0cc063586e`
- 상태: 계획 독립 감사 조건부 승인, 필수 보완 반영 후 구현 진입

## 1. 고정 목표

이 수리는 PR Studio 2.0의 고정 목표를 바꾸지 않는다.

> 사용자의 홍보 목적과 보유 자료를 이해하고, 목적에 맞는 콘텐츠를 기획한 뒤, 자연스러운 음성과 적절한 자막 및 화면으로 정확하게 전달하는 영상을 제작한다.

화려함이나 무조건적인 영상 생성을 늘리는 것이 목적이 아니다. 사용자가 명시적으로 선택한 영상 종류에 맞는 실제 화면과 자료를 기획 모델에 제공하여 콘텐츠 적절성 판단의 입력을 정확하게 만드는 것이 목적이다. 제작 게이트와 최대 3회 기획 제한은 그대로 유지한다.

## 2. 관찰된 결함

인증 사용자가 기존 MP4를 첨부하고 영상 종류를 `youtube`로 선택한 staging 작업에서 다음 현상이 재현되었다.

1. 작업 요청과 `planningBrief()`의 구조화된 브리프에는 `track: "youtube"`가 보존되었다.
2. 기존 MP4 분석은 정상 완료되어 길이, 프레임과 음성 증거가 수집되었다.
3. 화면 관찰 수집은 YouTube 제작 화면이 아니라 보도자료 작성 화면을 열었다.
4. 기획 모델은 요청한 YouTube 화면 증거가 없다고 판단했고, 3회 뒤 `plan_exhausted`로 종료했다.

`plan_exhausted` 자체는 실패가 아니다. 필요한 근거가 부족할 때 제작하지 않는 것은 의도된 안전장치다. 결함은 그 안전장치에 전달한 화면 근거가 사용자 선택과 달랐다는 점이다.

## 3. 근본원인

근본원인은 구조화된 사용자 의도를 하위 단계에서 다시 문자열 추론한 설계다.

호출 경로는 다음과 같다.

1. API 입력 경계와 워커의 `planningBrief()`는 요청의 `track`을 우선하고, 누락된 레거시 요청에만 `trackForBrief(purpose)`를 사용한다.
2. 워커는 수집기를 호출할 때 확정된 `brief.track`을 버리고 `brief.purpose`만 `CollectionContext.brief`로 전달한다.
3. 수집기는 `trackForBrief(context.brief)`를 다시 실행한다.
4. 목적 문장에 `유튜브`나 `쇼츠`라는 정확한 키워드가 없으면 휴리스틱의 기본값인 `press`가 선택된다.
5. 화면 관찰, fixture와 preset 수집이 잘못된 `press` 증거를 반환한다.

즉, Railway, OAuth, 로그인, MP4 업로드 또는 Playwright의 문제가 아니다. 명시적 필드보다 목적 문장 키워드를 뒤늦게 우선한 데이터 계약 위반이다.

## 4. 수리 원칙과 범위

### 선택한 수리

- `CollectionContext`는 목적 문자열 대신 필수 `track: VideoTrack`을 받는다.
- `collectPlanningOrders()`는 전달받은 `track`을 단일 진실 공급원으로 사용한다.
- 워커는 검증된 `brief.track`을 수집기에 전달한다.
- smoke 스크립트와 단위 테스트도 명시적 track을 전달한다.
- 명시적 `youtube`가 목적 문장이나 수집 지시의 표현과 무관하게 YouTube fixture/preset을 선택하는 회귀 테스트를 추가한다.
- 워커의 구조화된 브리프에서 수집 컨텍스트를 만드는 순수 함수를 분리하고, 목적 문장이 다른 종류를 암시해도 `brief.track`이 보존되는 경계 테스트를 추가한다.
- `press`, `news`, `youtube`별 화면 탭과 제목 매핑을 순수 함수로 분리해 표 기반 자동 테스트를 추가한다.
- 레거시 요청의 문자열 추론은 구조화된 브리프를 만드는 경계인 `planningBrief()`와 API 입력 경계에만 남긴다.

### 수리하지 않는 범위

- 제작 준비 기준을 낮추거나 `collect`를 `produce`로 강제하지 않는다.
- 기존 완료 작업과 감사 기록을 다시 쓰지 않는다.
- 자연어 수집 지시에서 영상 종류를 재추론하지 않는다.
- 화면 화려함, 전환 효과 또는 새로운 외부 도구를 추가하지 않는다.
- 재검증에서 별도로 재현되지 않는 모델 판단 문제까지 한 번에 수정하지 않는다.

## 5. 검토한 대안

### 목적 문장에 영상 종류를 덧붙이기 — 거절

현재 사례만 우회할 뿐 다른 호출자가 같은 실수를 반복할 수 있다. 표시용 문장을 제어 데이터로 사용하는 결합도 남는다.

### `trackForBrief()` 키워드 확대 — 거절

동의어를 늘려도 사용자의 명시적 선택과 문장 추론이 충돌할 수 있다. 추론 정확도 문제가 아니라 이미 확정된 값을 버리는 계약 문제다.

### 수집 지시문에서 종류 추론 — 거절

모델의 자유 문장은 모호하며 라운드마다 변할 수 있다. 모델 출력이 사용자 선택을 덮어쓰게 된다.

### 명시적 track 주입 — 채택

타입 검사로 누락된 호출자를 찾을 수 있고, 사용자 선택이 전체 파이프라인에서 보존된다. 가장 작은 변경으로 원인을 제거한다.

## 6. 수리가 가져올 수 있는 문제와 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 기존 직접 호출자가 `track`을 전달하지 않아 빌드 실패 | 개발 시 즉시 발견 | 모든 호출자를 검색해 수정하고 TypeScript 빌드로 확인 |
| 레거시 DB 작업에 `request.track`이 없음 | 영상 종류 결정 불가 가능성 | `planningBrief()`의 기존 1회 fallback 유지 |
| 과거 잘못된 수집 라운드가 남음 | 감사 기록 혼합 | 과거 기록은 불변으로 유지하고 새 작업으로 인수 검증 |
| 모델 수집 지시 문구와 사용자 track이 충돌 | 수집 보고가 지시와 다르게 보일 수 있음 | 사용자 track을 우선하며 보고에는 해당 track의 화면/프리셋 이름을 명시 |
| 수정 후에도 모델이 제작을 거부함 | 별도 기획 또는 증거 전달 결함 가능 | 제작을 강제하지 않고 새 작업의 라운드 증거로 다음 원인을 분리 진단 |
| 다른 track 회귀 | press/news 수집이 잘못될 수 있음 | 기존 테스트를 명시적 track으로 유지하고 youtube 우선성 회귀 테스트 추가 |

## 7. 궁극 목표 적합성 검토

- **콘텐츠 적절성:** 사용자 선택과 같은 종류의 실제 화면을 제공하므로 개선된다.
- **음성·자막 자연스러움:** 직접 변경하지 않는다. 잘못된 화면 근거가 내레이션과 자막 기획을 오염시키는 위험은 줄인다.
- **화면 적절성:** 화려함을 늘리지 않고 목적에 맞는 화면 선택 정확도만 높인다.
- **제작 안전성:** 제작 게이트, 콘텐츠 준비 검사와 3회 제한을 유지한다.
- **Railway 적합성:** 새 서비스나 외부 도구 없이 기존 워커 타입 계약만 수정한다.
- **도구 사용 원칙:** Playwright는 실제 화면 증거 수집이라는 품질 목적에만 계속 사용한다.

따라서 이 수리는 원래 앱의 방향을 바꾸지 않고, 오히려 사용자 의도와 수집 근거 사이의 불일치를 제거한다.

## 8. 구현 단계와 완료 조건

### 단계 A — 계획 독립 감사

- 이 문서와 관련 코드를 독립 감사자에게 제공한다.
- 근본원인, 최소 수리 범위, 목표 적합성, 회귀 위험과 검증 계획을 검토받는다.
- 감사 의견을 `수용`, `보류`, `거절`로 분류하고 근거를 기록한다.
- 치명적 또는 높은 위험의 미해결 지적이 없을 때만 구현한다.

### 단계 B — 타입 계약 수리

- `CollectionContext.brief`를 `CollectionContext.track`으로 교체한다.
- 수집기의 재추론을 제거한다.
- 워커와 모든 직접 호출자가 명시적 track을 전달하게 한다.

완료 조건: 저장된 사용자 선택이 화면 관찰, fixture와 preset 선택에 그대로 사용된다.

### 단계 C — 회귀 테스트와 정적 검증

- 명시적 YouTube track 우선성 테스트를 추가한다.
- 워커 브리프→수집 컨텍스트 경계와 세 종류 화면 라우팅 테스트를 추가한다.
- 관련 단위 테스트, 전체 테스트, lint와 build를 실행한다.

완료 조건: 키워드가 없거나 다른 종류를 암시하는 문구가 있어도 명시적 track이 우선하고 기존 press/news 경로가 통과한다.

### 단계 D — staging 배포와 끝단 인수

- 변경을 커밋하고 원격 `agent/pr-studio-2.0`에 푸시한다.
- Railway staging의 web과 worker가 같은 커밋으로 성공 배포됐는지 확인한다.
- 인증 세션에서 실제 MP4를 첨부하고 `youtube` 작업을 새로 생성한다.
- 수집 보고가 YouTube 콘텐츠 작성 화면을 관찰했는지 확인한다.
- 제작 여부와 무관하게 각 라운드의 판단이 실제 수집 증거와 일치하는지 확인한다.
- 영상이 생성되면 MP4 메타데이터와 화면·음성·자막·콘텐츠 일치를 검토한다.
- 영상이 생성되면 길이, 해상도, 파일 크기, 표본 프레임을 검사하고 최소 1회 전체 시청으로 음성-화면 동기와 자막 간결성을 확인한다.

완료 조건: 잘못된 보도자료 화면 수집이 재현되지 않고, 결과가 콘텐츠 게이트의 실제 판단으로 설명된다.

### 단계 E — 구현 독립 감사

- 구현 diff, 테스트 결과와 staging 증거를 독립 감사한다.
- 원인 제거 여부, 범위 초과 여부, 고정 목표와의 일치 여부를 판정한다.
- 미해결 높은 위험이 없을 때 수리를 완료로 표시한다.

## 9. 중단 조건

다음 중 하나가 발생하면 제작을 강제하지 않고 수리를 중단해 원인을 다시 분리한다.

- 명시적 track이 워커 또는 수집기에서 다시 소실된다.
- YouTube가 아닌 화면을 관찰한다.
- 인증/업로드/분석 실패가 새로 발생한다.
- 콘텐츠 준비 기준을 우회해야만 영상이 생성된다.
- 실제 산출물의 음성, 자막 또는 화면이 브리프와 명백히 어긋난다.
