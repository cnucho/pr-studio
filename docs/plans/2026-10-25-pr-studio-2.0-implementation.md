# PR Studio 2.0 구현 계획

- 작성일: 2026-10-25
- 작업 브랜치: `agent/pr-studio-2.0`
- 기준 커밋: `cb2fe71`
- 구현, 커밋, 푸시, Railway 배포는 각각의 명시적인 단계로 구분한다.

## 1. 고정된 궁극 목표

PR Studio 2.0의 궁극 목표는 화려한 영상을 자동 생성하는 것이 아니다.

> 사용자의 홍보 목적과 보유 자료를 이해하고, 목적에 맞는 콘텐츠를 기획한 뒤, 자연스러운 음성과 적절한 자막 및 화면으로 정확하게 전달하는 영상을 제작한다.

다음 우선순위는 모든 하위 설계와 구현 판단보다 우선한다.

1. 콘텐츠가 목적과 대상에 적절한가.
2. 장면 순서와 설명이 이해하기 쉬운가.
3. 음성이 자연스럽고 화면과 맞는가.
4. 자막이 간결하고 음성을 적절히 보완하는가.
5. 화면과 시각 요소가 전달 목적에 적절한가.
6. 해상도, 오디오, 파일 형식 등 기본 제작 품질을 충족하는가.
7. 시각 효과와 화려함은 위 항목을 방해하지 않는 범위에서만 사용한다.

궁극 목표는 구현 과정에서 변경하지 않는다. 하위 기능, 데이터 구조, 도구와 구현 방법은 이 목표를 더 잘 달성하는 경우에 한해 유연하게 변경할 수 있다.

## 2. 제품의 핵심 기능

PR Studio 2.0은 다음 순환을 한 작업 안에서 수행하는 콘텐츠 중심 영상 제작 에이전트다.

1. 사용자가 목적, 대상, 길이, 대략의 내용과 선택적인 기존 영상을 제공한다.
2. 앱은 영상 종류의 기본값, 사용 가능한 화면, 입력 자료와 도구 능력을 기획 모델에 제공한다.
3. 모델은 영상의 핵심 메시지, 장면 순서, 내레이션, 자막과 필요한 자료를 기획한다.
4. 앱은 수집 지시를 안전한 내부 기능에 연결하고 결과를 `있음` 또는 `없음`으로 보고한다.
5. 모델은 보고를 반영해 기획을 수정하거나 제작을 결정한다.
6. `decision`이 `produce`이고 콘텐츠 준비 기준을 통과한 경우에만 촬영과 합성을 시작한다.
7. 최종 MP4에서 음성, 자막, 화면, 길이와 콘텐츠 일치를 검토한다.

기획 모델 호출은 작업당 최대 3회다. 3회 안에 제작 결정이 없으면 영상을 만들지 않고 기획 기록과 수집 보고를 `plan_exhausted` 결과로 남긴다.

## 3. 설계 원칙

### 3.1 콘텐츠 우선

- 한 장면은 한 가지 핵심 의미를 전달한다.
- 모든 장면은 영상 목적과 연결된 이유가 있어야 한다.
- 내레이션은 화면에서 확인할 수 있는 사실을 설명한다.
- 자막은 내레이션 전문이 아니라 핵심 의미를 짧게 요약한다.
- 화면에 없는 수치, 기능, 효과를 만들지 않는다.
- 규칙 기반 결과를 모델이 직접 작성하거나 분석했다고 표현하지 않는다.
- 전달에 기여하지 않는 장면과 효과는 제거한다.

### 3.2 제작 게이트

- `collect` 응답으로는 촬영 스크립트를 실행하지 않는다.
- 모델 연결 실패나 잘못된 응답을 고정 대본 제작으로 대체하지 않는다.
- 제작 결정과 콘텐츠 준비 검사를 모두 통과해야 매니페스트를 고정한다.
- 고정된 매니페스트만 촬영, 음성, 자막과 합성 단계로 전달한다.

### 3.3 도구 사용

- 새로운 도구는 오류를 줄이거나 콘텐츠 및 제작 품질을 높일 때 적극적으로 사용한다.
- 도구 도입 자체를 제품 기능으로 간주하지 않는다.
- 같은 품질을 더 단순하고 안정적으로 달성할 수 있으면 자체 구현을 사용한다.
- 외부 도구는 버전을 고정하고 Railway Linux 환경에서 비대화 없이 실행 가능해야 한다.
- 자유 문장 수집 지시는 임의 shell 명령으로 실행하지 않고 등록된 수집기에만 연결한다.

### 3.4 Railway 실행

- 웹 서비스는 요청 검증, 작업 생성, 상태 조회와 결과 제공을 담당한다.
- 워커는 기획, 수집, 제작과 검토를 담당한다.
- 작업 상태와 회차는 DB에 저장해 워커 재시작 후 이어서 실행한다.
- 모든 임시 파일은 작업 ID별 디렉터리에 격리한다.
- 웹은 `npm start`, 워커는 `npm run worker:video`로 실행한다.

## 4. 단계별 감사 원칙

각 구현 단계는 다음 절차를 따른다.

1. 단계 계획 작성
2. 계획 감사
3. 계획 감사 중 궁극 목표에 도움이 되는 의견 반영
4. 구현
5. 자동 테스트와 실행 증거 수집
6. 구현 감사
7. 감사 결과 분류 및 필요한 수정
8. 단계 완료 조건 확인 후 다음 단계 진입

감사는 방향을 새로 정하는 절차가 아니다. 감사 의견은 다음 기준으로 처리한다.

- `수용`: 궁극 목표 또는 해당 단계 목표 달성도를 높인다.
- `수정 수용`: 좋은 취지는 유지하되 현재 구조에 맞게 범위를 조정한다.
- `보류`: 유용하지만 현재 단계의 핵심 기능과 직접 관련되지 않는다.
- `거절`: 궁극 목표를 흐리거나 화려함, 도구 도입, 구조 변경 자체를 목적으로 한다.

각 단계 감사 기록에는 최소한 다음을 남긴다.

- 감사 대상 커밋 또는 작업 트리 상태
- 고정 목표와의 일치 여부
- 단계 완료 기준별 증거
- 발견된 문제와 처리 결정
- 다음 단계 진입 가능 여부

감사 기록은 `docs/audits/pr-studio-2.0-stage-<번호>.md`에 저장한다.

## 5. 현재 코드 기준선

현재 코드에는 다음 기반이 있다.

- `lib/video-beats.ts`: 영상 종류별 프리셋, 화면, fixture와 매니페스트 생성
- `lib/video-agent.ts`: 단발 기획 호출과 촬영·렌더링·검토 실행
- `scripts/capture-video-v2.mjs`: Chromium 화면 촬영
- `scripts/render-video-v2.mjs`: 음성, 카드, 자막과 MP4 합성
- `scripts/review-video-v2.mjs`: 해상도, 오디오와 촬영 기록 검사
- `scripts/video-agent-worker.mjs`: Supabase 작업 claim 및 제작
- `supabase/migrations/202607220001_video_agent_queue.sql`: 기본 작업 큐
- `Dockerfile`: Chromium, FFmpeg, Noto CJK, Tesseract 환경

현재 구현은 기획 응답 한 번을 받은 뒤 `decision`과 관계없이 제작한다. 수집 지시와 보고의 다음 회차 전달, 회차 저장, 작업별 파일 격리, 기존 MP4 입력과 최종 MP4 기반 콘텐츠 검토는 구현되지 않았다.

## 6. 단계별 구현 계획

### 단계 1. 콘텐츠 기획 계약과 제작 게이트

#### 목표

궁극 목표를 코드가 표현할 수 있도록 기획 결과, 수집 지시, 콘텐츠 점검과 제작 결정을 명시적인 계약으로 만든다.

#### 구현

- 구조화된 `VideoBrief`를 정의한다.
- `PlanningRound`, `CollectionOrder`, `CollectionReport`를 정의한다.
- 목적 적합성, 대상 적합성, 장면 논리, 근거, 음성, 자막과 화면 적절성을 담는 `ContentReview`를 정의한다.
- 기획 응답의 `collectionOrders`, `contentReview`, `decision`을 버리지 않고 저장한다.
- `decision === produce`와 콘텐츠 준비 조건을 모두 통과한 경우에만 제작 가능 상태로 만든다.
- 영상 종류에 맞는 화면과 공통 화면만 선택할 수 있게 한다.
- 입력 길이와 모델 출력 길이를 제한한다.

#### 완료 조건

- `collect` 응답은 촬영으로 이어지지 않는다.
- 기획 결과에 콘텐츠 적절성 판단과 미해결 문제가 남는다.
- 다른 영상 종류의 화면이 매니페스트에 들어가지 않는다.
- 모델 실패가 자동 제작으로 바뀌지 않는다.
- 단위 테스트로 위 조건을 증명한다.

### 단계 2. 작업 상태와 회차 영속화

#### 목표

웹 요청과 워커 실행을 분리하고, 기획 순환을 Railway에서 중단 후 재개할 수 있게 한다.

#### 구현

- API는 입력을 검증하고 작업만 생성한 뒤 `202`와 작업 ID를 반환한다.
- 작업에 `phase`, `outcome`, `planning_round`, `final_decision`, `manifest`, `artifact_prefix`를 저장한다.
- 기획 회차와 수집 보고는 별도 `video_agent_planning_rounds` 테이블에 저장한다.
- 워커 lease heartbeat를 추가한다.
- 각 단계 완료 후 checkpoint를 저장한다.
- 동일 단계 재실행이 결과를 손상하지 않도록 idempotency를 적용한다.

#### 완료 조건

- 모델 호출 전에 작업이 DB에 존재한다.
- 워커 종료 후 마지막 완료 단계부터 재개한다.
- 재시도하더라도 모델 호출 누계가 3회를 넘지 않는다.
- 긴 작업이 lease 만료로 중복 실행되지 않는다.

### 단계 3. 자료 수집기와 3회 기획 순환

#### 목표

모델의 자유 문장 수집 지시를 실제 앱 능력에 안전하게 연결하고, 결과를 다음 기획 회차에 반영한다.

#### 구현

- fixture 수집기
- 프리셋 수집기
- Chromium 화면 관찰 수집기
- HTML 카드 가능성 수집기
- 기존 영상 분석 수집기
- 알 수 없는 지시의 `없음` 보고
- 최대 3회의 기획→수집→재기획 orchestration
- 매 회차 입력, 출력과 보고 저장

수집 지시 문장은 자유롭게 유지하되, 모델 응답에는 실행 연결을 위한 `capabilityId`를 함께 받는다. 앱은 등록된 capability만 실행한다.

#### 완료 조건

- 수집 보고가 다음 모델 요청 본문에 포함된다.
- 가능한 수집은 실제 값 또는 파일 경로를 반환한다.
- 불가능한 수집은 이유가 포함된 `없음`을 반환한다.
- 3회 안에 `produce`가 없으면 `plan_exhausted`로 끝난다.

### 단계 4. 콘텐츠 중심 매니페스트 확정

#### 목표

제작 입력이 화면 목록이 아니라 목적, 근거, 내레이션과 자막이 연결된 콘텐츠 계획이 되게 한다.

#### 구현

각 beat에 다음을 고정한다.

- 장면 목적
- 시청자가 이해할 핵심
- 사용 근거
- 화면과 동작
- 내레이션
- 자막
- 다음 장면으로 넘어가는 이유
- 최소 화면 유지 시간과 발화 예상 시간

매니페스트 확정 시 다음을 검사한다.

- 목적 및 대상과 장면의 관련성
- 입력→실행→결과의 논리
- 근거 없는 주장
- 음성과 화면 불일치
- 자막과 내레이션의 불필요한 중복
- 예상 영상 길이

#### 완료 조건

- 브리프가 달라지면 핵심 메시지, 장면 순서와 문장이 달라진다.
- 모든 장면에 목적과 근거가 있다.
- 자막은 내레이션 전체 복사가 아니다.
- 제작 스크립트는 확정된 매니페스트 외의 고정 대본을 사용하지 않는다.

### 단계 5. 작업별 촬영·음성·자막·합성

#### 목표

확정된 콘텐츠를 과장 없이 자연스럽고 안정적으로 영상화한다.

#### 구현

- 모든 스크립트에 `--work-dir`, `--manifest`, `--output` 인자를 추가한다.
- 작업별로 화면, 음성, 카드, 클립과 최종 파일을 격리한다.
- 동작 beat는 실제 시작·종료 범위만 사용하고 부족한 길이는 마지막 프레임으로 채운다.
- 한국어 음성 provider, voice와 속도를 프리셋에서 강제한다.
- 음성 합성 실패를 다른 provider로 조용히 대체하지 않는다.
- 자막 문자열을 ASS 형식에 안전하게 변환한다.
- 표와 도식은 설명에 필요한 경우에만 생성한다.

#### 완료 조건

- 두 작업을 동시에 실행해도 파일이 섞이지 않는다.
- 내레이션이 해당 화면 동작 범위를 벗어나지 않는다.
- 음성 provider와 자막 설정이 매니페스트와 일치한다.
- 결과물이 1920×1080 MP4이며 오디오가 있다.

### 단계 6. 최종 영상 콘텐츠 검토

#### 목표

렌더 명령 성공이 아니라 최종 영상이 의도한 콘텐츠를 제대로 전달하는지를 확인한다.

#### 구현

- 최종 MP4 타임라인에서 beat별 표본 프레임을 추출한다.
- OCR로 최종 화면의 핵심 문구를 확인한다.
- 오디오, 해상도, 길이와 파일 크기를 검사한다.
- 자막 위치, 잘림과 표시 시간을 검사한다.
- 매니페스트, 내레이션, 자막과 화면 근거의 대응 기록을 생성한다.
- `review.json`과 표본 프레임을 결과 저장소에 보관한다.

#### 완료 조건

- Tesseract가 없거나 최종 프레임 검사가 실패하면 합격하지 않는다.
- 최종 영상 길이가 프리셋 범위에 든다.
- 각 beat의 핵심 근거가 최종 영상에서 확인된다.
- 기술 검사를 통과해도 콘텐츠 불일치가 있으면 제작 완료로 처리하지 않는다.

### 단계 7. 기존 MP4 분석과 Railway 배포

#### 목표

기존 영상을 참고하는 기획과 전체 2.0 순환을 Railway 워커 한 번으로 실행한다.

#### 구현

- 인증된 비공개 Storage 업로드와 `sourceVideoId`를 추가한다.
- 기존 MP4를 작업 디렉터리로 다운로드한다.
- Docker에 이미 포함된 FFmpeg/FFprobe, OpenAI 공식 음성 전사 API와 선택적인 Tesseract OCR을 조합한 제한형 분석기를 사용한다.
- 시간표, 대사, OCR과 제한된 프레임을 1차 기획 자료에 포함한다.
- MP4 원본은 모델 API에 첨부하지 않는다.
- analyzer cache, timeout, 출력 크기와 파일 경로를 제한한다.
- Railway 웹과 워커 환경 변수 및 health check를 문서화하고, HTTP 서버가 없는 worker는 별도 Dockerfile로 분리한다.

#### 완료 조건

- 기존 MP4가 있는 작업만 analyzer를 호출한다.
- 외부 URL이나 임의 로컬 경로를 analyzer 입력으로 받지 않는다.
- 웹 재시작과 워커 재시작 후 작업 조회 및 재개가 가능하다.
- Railway에서 기획, 수집, 제작과 검토가 한 작업으로 끝난다.

### 단계 8. UI와 최종 인수 검사

#### 목표

사용자가 콘텐츠 기획 과정, 수집 결과, 제작 결정과 최종 결과를 이해할 수 있게 한다.

#### 구현

- 시간 기반 가짜 진행 표시를 실제 `phase`와 회차 정보로 교체한다.
- 기획 회차, 수집 보고와 콘텐츠 점검을 표시한다.
- `plan_exhausted`를 실패와 구분한다.
- 영상이 없는 결과에서도 기획과 부족한 자료를 확인할 수 있게 한다.
- 페이지를 닫았다가 다시 열어도 작업을 재조회할 수 있게 한다.

#### 최종 인수 기준

1. 브리프의 목적과 대상이 최종 콘텐츠에 반영된다.
2. 한 장면이 한 가지 의미를 전달한다.
3. 모든 주요 주장에 자료 또는 화면 근거가 있다.
4. 내레이션은 자연스럽고 화면에 보이는 내용을 설명한다.
5. 자막은 짧고 내레이션을 적절히 보완한다.
6. 효과를 제거해도 콘텐츠만으로 영상이 성립한다.
7. `produce` 이전에는 촬영이 실행되지 않는다.
8. 3회 안에 제작 준비가 되지 않으면 영상 없이 기록을 남긴다.
9. 최종 MP4에서 화면, 음성, 자막과 콘텐츠 일치를 확인한다.
10. Railway 워커가 중단과 재시도 상황에서도 같은 작업을 안전하게 완료한다.

## 7. 범위에서 제외하는 것

- 화려함 자체를 목적으로 한 모션 그래픽 시스템
- 범용 영상 편집기
- 임의 shell 명령을 수행하는 자율 에이전트
- 원본 MP4를 모델 API에 직접 첨부하는 기능
- 데스크톱 대화창 MCP를 Railway 실행 경로로 사용하는 방식
- 콘텐츠 품질과 직접 관계없는 외부 도구 도입
