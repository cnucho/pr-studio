# PR Studio 2.0 증거 생명주기·상호작용 수집 후속 수리 계획

- 작성일: 2026-10-26
- 기준 커밋: `f33c09c`
- 발견 작업: `8a69f49f-9945-495b-8aab-984e25d0d2c4`
- 상태: 독립 계획 감사 지적 반영 완료, 구현 진입 승인

## 1. 고정 목표

PR Studio 2.0은 화려한 영상을 무조건 만드는 도구가 아니다. 사용 목적과 자료에 맞는 콘텐츠를 기획하고, 자연스러운 음성·간결한 자막·목적에 맞는 화면으로 정확하게 전달할 준비가 되었을 때만 제작한다.

이번 수리의 목표는 제작 게이트를 낮추는 것이 아니라, 게이트가 실제로 수집한 증거 전체를 기억하고 앱이 약속한 범위의 검증 가능한 화면 증거를 제공하게 하는 것이다.

## 2. 재현 결과

track 수리 후 실제 YouTube 작업에서 다음이 확인되었다.

1. 기존 MP4 52.6초 분석에 성공했다.
2. YouTube 제작 화면을 정확히 선택했다.
3. 화면 수집기는 초기 화면 문구만 읽고 정책자료 입력, 생성 클릭과 결과 확인은 하지 않았다.
4. 모델은 생성 후 `대본`과 `YouTube 게시 패키지` 증거가 없다고 판단했다.
5. 3차 기획은 같은 작업 기록에 MP4 분석 보고가 있는데도 기존 영상 분석 결과가 없다고 판단했다.
6. 게이트는 영상을 억지로 만들지 않고 `plan_exhausted`로 종료했다.

## 3. 근본원인 A — 증거 생명주기

- orchestration은 각 수집 후 `reports`를 새 배열로 덮어써 과거 증거를 잃는다.
- 워커 재개 시 저장된 모든 라운드가 아니라 마지막 라운드의 보고만 복원한다.
- 모델 프롬프트도 보고를 `직전 수집 보고`로 설명한다.
- 3차 기획 뒤 수집을 한 번 더 실행하지만 최대 3회 제한 때문에 그 결과를 판단할 기획 호출이 없다.

그 결과 한 라운드에서 확인한 MP4, 화면 또는 프리셋 증거가 다음 라운드에서 재요청되지 않으면 사라지고, 마지막 수집은 비용과 기록만 만들 뿐 의사결정에 쓰이지 않는다.

## 4. 근본원인 B — 화면 수집 계약 불일치

기획 dossier의 Chromium 능력은 입력, 클릭, 결과 확인과 동작 녹화를 할 수 있다고 설명한다. 실제 `screen-observation` 수집기는 종류별 탭을 클릭한 뒤 초기 화면 `innerText()`만 반환한다.

모델의 자연어 지시를 임의 실행하는 기능은 안전하지 않지만, 등록된 세 track에 대해 앱이 보유한 fixture를 입력하고 정해진 생성/분석 버튼을 누른 뒤 결과 표식을 확인하는 결정론적 시나리오는 안전하게 제공할 수 있다.

## 5. 선택한 수리

### 누적 증거

- orchestration은 새 보고를 기존 보고 뒤에 누적해 다음 기획에 전달한다.
- 워커 재개 시 저장된 모든 라운드의 보고를 순서대로 복원한다.
- 프롬프트 표현을 `누적 수집 보고`로 바꾼다.
- 저장용 원본 라운드 보고와 모델 입력용 정규화 보고를 분리한다.
- 모델 입력은 `capabilityId + track + source identity/scenario version`이 같은 증거를 한 번만 포함하며 성공 보고를 실패 보고보다 우선한다.
- evidence 값별 상한과 전체 직렬화 문자 예산을 코드 상수로 고정하고, 초과한 값에는 잘림 표식을 남긴다.
- 이미 성공한 capability는 같은 작업의 다음 회차에서 다시 실행하지 않는다.
- 같은 수집 배치에서 `video-analysis`와 `screen-observation`은 각각 단일 Promise를 공유한다.

### 최종 회차 의미

- 3차 기획의 모델 decision 계약은 기존처럼 `produce | collect`를 유지한다.
- 준비 완료면 `produce`, 미완료면 `collect`와 실제 차단 항목을 반환한다.
- orchestration은 3차의 `collect`를 `plan_exhausted` outcome으로 변환한다.
- 3차 결과가 `collect`여도 판단되지 않을 새 수집을 실행하지 않는다.
- 시스템 지시에 3차 회차에서는 새 수집 지시가 아니라 현재 증거에 따른 최종 판정을 하도록 명시한다.
- 최대 모델 호출 3회 원칙은 유지한다.

### 결정론적 화면 상호작용

- track별 입력 필드, fixture 값, 실행 버튼과 결과 표식을 코드에 명시한다.
- `press`: 정책명·사업내용·예산·대상·기대효과 입력 → 생성 → 보도자료 결과 확인
- `news`: 기사 입력 → 분석 → 분석 결과 확인
- `youtube`: 정책자료 텍스트·대상·영상 길이 입력 → 생성 → `YouTube 게시 패키지` 확인
- 모델의 자유 문장을 selector나 스크립트로 해석하지 않는다.
- 앱 화면에 수집 전용 `data-*` contract/version, field, action, loading/error, result-ready 표식을 추가한다.
- 서버가 설정한 `PR_STUDIO_CAPTURE_URL` origin을 워커의 필수 신뢰 경계로 사용하고 저장된 `app_url`과 정확히 일치시킨다.
- 최초 URL과 리디렉션 뒤 URL의 origin을 모두 재검사하고 PR Studio 수집 contract/version 표식이 없으면 입력·클릭하지 않는다.
- 결과-ready가 나타나고 loading이 끝났으며 오류 표식이 없을 때만 `있음`으로 보고한다.
- 화면 전체가 아니라 해당 결과 컨테이너의 제한된 텍스트만 증거로 수집한다.
- 보고 provenance에 track, round, scenario version, fixture/source identity와 result marker를 남긴다.
- 같은 라운드의 복수 화면 요청은 한 번의 상호작용 결과를 공유한다.
- 실패 시 원인을 포함한 `없음` 보고를 반환해 게이트가 안전하게 멈추게 한다.
- Chromium 능력 설명을 실제 기획 수집과 제작 단계의 역할에 맞게 수정한다.

### 제작 전·후 게이트 책임 정렬

- 제작 전 기획은 콘텐츠 계획, 실제 앱 입력·결과 증거, 사용 가능한 카드/음성/자막 capability와 preset을 판단한다.
- 카드 이미지, 합성 음성, 적용된 자막과 최종 MP4는 `produce` 뒤 제작·최종 검토 단계에서 생성하고 검증한다.
- 모델이 제작 전 단계에서 아직 존재할 수 없는 최종 카드 이미지나 합성 결과를 차단 조건으로 요구하지 않도록 시스템 계약에 명시한다.
- 이는 검사를 생략하는 것이 아니라 최종 산출물 검사를 원래 단계로 되돌리는 것이다.

## 6. 대안 검토

### 제작 게이트 완화 — 거절

증거가 없는데도 제작하면 사용자 목표와 정면으로 충돌한다.

### 4차 모델 호출 추가 — 거절

마지막 수집을 판단할 수 있지만 고정된 최대 3회 원칙과 비용·지연 한계를 바꾼다.

### 과거 계획 요약만 믿기 — 거절

이전 모델의 해석에는 원본 수집 보고가 빠져 있어 같은 기억 소실을 반복한다.

### 자연어 지시를 브라우저 명령으로 변환 — 거절

모델 출력에 임의 실행 권한을 주며 selector 변동과 보안 위험이 커진다.

### 등록된 track 시나리오 실행 — 채택

앱이 통제하는 fixture와 selector만 사용하면서 모델이 요구하는 실제 결과 증거를 제공한다.

### 최종 산출물을 제작 전에 생성 — 거절

제작 승인 전 카드·음성·자막·MP4를 미리 만들면 게이트의 의미가 사라지고 비용이 중복된다. 제작 전에는 capability와 preset을, 제작 후에는 실제 산출물을 검증한다.

## 7. 예상 부작용과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 누적 보고로 프롬프트 증가 | 비용·지연·요청 실패 | provenance 중복 제거, 값별 상한, 전체 문자 예산, 잘림 표식 |
| 반복 MP4 분석·화면 생성 | 브라우저·CPU·전사 시간 증가 | 성공 capability 재사용, 배치 안 단일 Promise 공유 |
| UI label 변경 | 수집 실패 | track 시나리오 표 기반 테스트와 staging 실제 작업으로 확인 |
| 결과 API 지연·실패 | 기획 수렴 실패 | 명시적 timeout과 `없음` 보고, 제작 강행 금지 |
| 3차에 새 증거 요청 | 요청 미실행 | 최종 회차 계약을 prompt와 orchestration에 함께 고정 |
| 과거 작업 재개 시 중복 보고 | 프롬프트 중복 | 저장 순서 보존; 필요하면 완전 동일 보고만 안정적으로 중복 제거 |
| 변조된 app URL에서 입력·클릭 | 외부 사이트에 능동 요청 | 환경 origin 일치, redirect 재검사, 앱 contract marker 확인 |

## 8. 목표 적합성 검토

- 콘텐츠 적절성: 근거가 사라지지 않고 실제 결과 화면이 제공되므로 향상된다.
- 음성·자막: 실제 화면 결과를 기준으로 내레이션과 자막을 기획할 수 있다.
- 화면 적절성: 화려함이 아니라 입력→실행→결과라는 설명 목적에 맞는 화면을 확인한다.
- 제작 안전성: 게이트와 최대 3회 제한을 유지하며 증거 부족 시 계속 멈춘다.
- Railway 적합성: 기존 Chromium과 앱 API만 사용하고 새 인프라·외부 도구를 추가하지 않는다.

## 9. 구현 단계와 완료 조건

### A. 계획 독립 감사

- 증거 누적 방식, 최종 회차 의미, 결정론적 상호작용의 안전성과 목표 적합성을 감사한다.
- 높은 위험의 미해결 지적이 없을 때 구현한다.

### B. 증거 생명주기 수리

- 새 보고를 누적하고 저장된 모든 라운드 보고를 복원한다.
- 모델 입력용 보고를 provenance 기준으로 중복 제거하고 문자 예산 안으로 제한한다.
- 성공한 capability와 배치 내 video analysis를 중복 실행하지 않는다.
- 3차에는 미사용 수집을 실행하지 않는다.
- 프롬프트의 누적 증거·최종 회차 계약을 명시한다.

완료 조건: 1차 MP4 보고가 2·3차 입력에도 남고, `collect`로 끝난 3차에서 수집기가 다시 호출되지 않는다.

### C. 화면 상호작용 수리

- 세 track의 결정론적 입력·실행·결과 확인 시나리오를 구현한다.
- 신뢰 origin과 redirect origin, 앱 contract/version을 검증한다.
- 안정적인 `data-*` field/action/result/error 표식을 사용한다.
- 실제 결과 텍스트를 수집 보고에 포함한다.
- Chromium 능력 설명을 구현과 일치시킨다.

완료 조건: YouTube 수집 증거에 초기 `결과 대기 중`이 아니라 생성된 `대본`과 `YouTube 게시 패키지`가 포함된다.

### D. 자동 검증

- 증거 누적, 저장 복원, 최종 회차 무수집 테스트를 추가한다.
- 반복 분석 주문, 누적 중복 제거·문자 예산, 2회 저장 후 재개와 3회 저장 후 재개를 테스트한다.
- 허용/불허 origin과 redirect 후 origin 검사를 테스트 가능한 순수 계약으로 고정한다.
- track별 상호작용 시나리오 매핑 테스트를 추가한다.
- 전체 test, lint, production build를 통과한다.

### E. staging 끝단 인수

- web·worker가 같은 새 커밋으로 성공 배포됐는지 확인한다.
- 같은 실제 MP4와 YouTube 브리프로 새 작업을 실행한다.
- 모든 회차에서 MP4 증거가 유지되고 생성 후 화면 결과가 보고되는지 확인한다.
- `produce`면 최종 MP4의 길이·해상도·파일 크기·표본 프레임·전체 시청·음성/화면 동기·자막 간결성을 확인한다.
- `plan_exhausted`면 남은 차단 항목이 실제 누락 증거와 일치하는지 확인한다.

### F. 구현 독립 감사

- diff, 자동 검증과 실환경 증거를 독립 감사한다.
- 높은 위험이 없고 고정 목표를 훼손하지 않을 때 단계 완료로 판정한다.
